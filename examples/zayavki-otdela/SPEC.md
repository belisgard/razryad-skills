# SPEC: Реестр заявок

Ветка: продукт с интерфейсом (по вердикту `PRD.md`)
Статус: согласована

## Как работает

### Ветка «продукт»
- Кто открывает и что видит первым: любой из четверых (3 менеджера + владелец) открывает страницу и сразу
  видит общий список всех заявок от всех менеджеров, без входа по логину и паролю.
- Главный сценарий, «действие → что происходит»:
  1. Менеджер нажимает кнопку «Новая заявка» → открывается форма с полями: своё имя (выбор из списка трёх
     менеджеров), клиент, что нужно, срок, сумма (необязательно).
  2. Менеджер заполняет обязательные поля (клиент, что нужно, срок) и нажимает «Сохранить» → заявка
     появляется в общем списке со статусом «новая», без обновления страницы вручную кем-либо ещё.
  3. Любой из четверых меняет статус заявки прямо в строке списка через выпадающий список
     (новая / в работе / сделано / отменено) → статус меняется, изменение сразу видно остальным.
  4. Владелец или менеджер фильтрует список по статусу → видит только заявки нужного статуса.
- Данные на входе: имя менеджера (выбор из списка трёх), клиент (свободный текст, без контактов), что нужно
  (свободный текст), срок (дата из календаря, формат ДД.ММ.ГГГГ), сумма (число, необязательно).
- Данные на выходе: общий список заявок со столбцами клиент, что нужно, срок, сумма, статус, автор (имя
  менеджера); список хранится в общем месте, доступен и без компьютера владельца.

## Что значит «правильно»

- Заявка, внесённая одним менеджером, появляется в общем списке сразу и видна остальным троим без чьих-либо
  действий по обновлению.
- Смена статуса одним из четверых сразу видна остальным в том же списке.
- В списке нет ни одной заявки, потерянной или не попавшей в свод: всё, что менеджер внёс, есть в списке.

## Крайние случаи

| Ситуация | Что делает инструмент |
|---|---|
| Пустое обязательное поле (клиент, что нужно или срок) при сохранении | Форма не сохраняет заявку, подсвечивает пустое поле |
| Менеджер дважды нажал «Сохранить» на той же заявке (дубль) | Дубль не блокируется; появляются две заявки, менеджер вручную переводит лишнюю в статус «отменено» |
| Нужно убрать заявку из активных | Удаления заявок нет вообще; единственный способ - сменить статус на «отменено», запись остаётся в списке |
| Сумма не указана | Поле сохраняется пустым, это допустимо (сумма необязательна) |

## Примеры «вход → верный выход»

### Пример 1: менеджер вносит новую заявку
- Вход: менеджер выбирает своё имя «Аня» в форме; клиент «Клиент 1»; что нужно «Замена окна на балконе»;
  срок 10.09.2026; сумма не указана. Нажимает «Сохранить».
- Верный выход: в общем списке появляется новая строка: клиент «Клиент 1», что нужно «Замена окна на
  балконе», срок «10.09.2026», сумма пусто, статус «новая», автор «Аня».
- Как проверить: владелец или другой менеджер открывает список (без обновления кем-то вручную) и сразу
  видит эту строку.

### Пример 2: смена статуса на «в работе»
- Вход: в строке заявки клиента «Клиент 1» (из примера 1) менеджер выбирает в выпадающем списке статус
  «в работе».
- Верный выход: статус строки меняется на «в работе», остальные поля заявки (клиент, что нужно, срок,
  сумма, автор) не меняются.
- Как проверить: владелец открывает список и видит статус «в работе» у этой заявки без своих действий.

### Пример 3 (крайний случай): попытка сохранить заявку с пустым сроком
- Вход: менеджер заполняет клиент «Клиент 2», что нужно «Консультация по товару», поле «срок» оставляет
  пустым, нажимает «Сохранить».
- Верный выход: заявка не сохраняется, форма подсвечивает поле «срок» как обязательное, новая строка в
  списке не появляется.
- Как проверить: попробовать сохранить с пустым сроком, увидеть подсветку поля и отсутствие новой заявки
  в общем списке.

## Вне объёма

- Не считает деньги/суммы по заявкам, только статусы.
- Не напоминает автоматически, если заявка долго висит без движения.
- Не хранит историю переписки с клиентом, только факт заявки и её статус.
- Не различает права доступа - любой из четверых видит и правит весь список.
- Не хранит контакты клиента (телефон и т.п.), только имя/название.
- Нет удаления заявок, нет сводки-счётчика по статусам, нет сортировки по менеджеру или дате.

## Устройство

Макет пройден и принят человеком 02.09.2026 (`mockup/index.html`), сценарий совпал с описанным в этом файле
без правок.

- **Нужна ли нейросеть внутри: нет.** Это точный список с фиксированными статусами: добавление и чтение
  строк, без анализа текста и без прогнозов. Нейросеть не даёт здесь выгоды и вносит риск неточности там,
  где нужен точный счёт.
- **Части решения:**
  1. Страница - то, что открывают менеджеры и владелец: список заявок и форма, как в макете.
  2. Хранилище - общее место для заявок, доступное всем четверым, работает без компьютера владельца.
  3. Автообновление - страница сама подтягивает новые заявки и смены статуса у остальных, без ручного
     обновления страницы.
- **На чём делаем:**
  - Хранилище: Google Таблица + Google Apps Script как простое API поверх неё. Владелец уже умеет работать
    с таблицами, сможет открыть и посмотреть данные напрямую; ничего дополнительно администрировать не надо.
  - Страница: HTML-страница на основе макета, подключённая к хранилищу, выложена на бесплатный статический
    хостинг (например GitHub Pages).
  - Обновление у всех: страница опрашивает таблицу каждые несколько секунд, этого достаточно для «сразу
    видно остальным» из приёмочных критериев.
- **Оценка стоимости: 0 ₽/мес.** Как посчитано: бесплатные тарифы Google Таблиц, Apps Script и статического
  хостинга покрывают нагрузку в десятки заявок в день с большим запасом.
