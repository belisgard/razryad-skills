# Рубрика приёмки для первого инструмента

Приёмка это договорённость о готовом, проверенная по пунктам. Расплывчатые пункты дают расплывчатую
приёмку, поэтому сначала список пунктов, потом вердикты. Список берётся из `SPEC.md`, не из головы.

## Хороший пункт даёт «готово / не готово» без толкований

| Плохо (не проверить) | Хорошо (проверяется за минуту) |
|---|---|
| «Поиск работает корректно» | «Ввожу “Иванов” в поиск, вижу две заявки с этой фамилией из тестовых данных и ни одной чужой» |
| «Ничего не сломано» | «После перезапуска все 20 тестовых записей на месте» |
| «Отчёт красивый» | «В отчёте колонки: дата, клиент, сумма; суммы до рубля; итог внизу совпадает с суммой строк» |
| «Ошибки обрабатываются» | «Кладу пустой файл на вход, получаю сообщение “файл пустой”, инструмент не падает» |

Если пункт спеки сформулирован плохо, не проверяй его «примерно». Спроси человека, как он поймёт,
что пункт выполнен, и запиши конкретную формулировку в `TODO.md` рядом с вердиктом.

## Четыре зоны

Пункты собираются по четырём зонам. Пустая зона это тоже сигнал: спроси человека, точно ли там нечего проверять.

1. **Сценарии.** Главный путь от начала до результата и побочные пути, которые описаны в `SPEC.md`.
2. **Крайние случаи.** Пустой вход, дубль, битый файл, очень длинное значение, повтор действия дважды.
3. **Состояния экрана** (если есть интерфейс). Что видно при загрузке, при ошибке, при пустых данных.
4. **Доступы.** Кто не должен мочь: чужие записи, удаление без подтверждения, открытие без пароля, если он задуман.

Ориентир: 5-15 пунктов. Меньше пяти: скорее всего спека тонкая, скажи об этом. Больше двадцати: приёмка
разбивается на два захода, сначала главный сценарий и примеры, потом остальное.

## Таблица вердиктов

| # | Пункт | Вердикт | Доказательство |
|---|---|---|---|
| 1 | Ввожу «Иванов», вижу две заявки | готово | скриншот `data/acceptance/01.png` |
| 2 | Пустое имя не сохраняется | не готово: сохраняется без подсказки | вывод прогона, запись № 21 в базе |

Доказательство это то, что человек может открыть и увидеть сам: вывод команды, скриншот, файл результата.
«Проверил, работает» доказательством не является. Вердикт без доказательства не вердикт.

## Примеры «вход → верный выход»

Каждый пример из `SPEC.md` прогоняется на реальном инструменте, не «по коду». Показывать так:

| Пример | Вход | Ожидаемый выход | Фактический выход | Вердикт |
|---|---|---|---|---|
| 1 | файл `data/test/postavka-1.xlsx` | 18 строк, из них 3 с пометкой «НЕТ» | 18 строк, 3 «НЕТ» | готово |
| 2 | строка с артикулом «АБС-123/1» | найден товар «АБС 123 1» | не найден | не готово |

Совпало до значения: готово. «Почти совпало» это не готово.

## Ключ ответов

Если `razryad-data` оставил в `data/README.md` список зашитых находок (дубли, ошибки, пропуски), сверь
по нему: должен был найти / нашёл / пропустил / нашёл лишнего. Пропуск и ложная находка оба «не готово».

## Против самозащиты агента

Агент, который сам собирал, склонен считать результат правильным. Приёмы:

- Человек проходит главный сценарий сам, до того как агент показывает свои вердикты.
- Агент показывает выход, а не пересказывает его. Файл, скриншот, вывод команды.
- Расхождение со спекой всегда «не готово». Если спека кажется неверной, это отдельный вопрос человеку,
  а не повод переписать ожидаемый результат под фактический.
- Слова «в целом», «почти», «мелочь», «особенность данных» в вердиктах не используются.
- Нашёл дыру, запиши. Чинить посреди приёмки нельзя: теряется ход проверки, а исправленное не перепроверяется.

## Три корзины

- **Сейчас**: без этого выпускать нельзя. Обычно: главный сценарий даёт неверный результат, теряются данные,
  виден чужой доступ. Про каждый пункт переспросить: точно ли нельзя выпустить без него.
- **Потом**: после выпуска, на следующих заходах. Удобство, побочные сценарии, косметика.
- **Никогда**: сознательно не делаем, с причиной. «Печать в PDF: коллеги работают только в браузере».

Корзину выбирает человек. Агент предлагает, если спросят, но не раскладывает сам.
